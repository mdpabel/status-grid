`503 Service Unavailable` and `429 Too Many Requests` both tell a client that access is temporarily limited, but they describe different causes.

## Use 503 for temporary server unavailability

A 503 says the server cannot handle the request right now, commonly because of maintenance or overload. It is a better signal than returning a normal-looking 200 page that says “maintenance” while the actual content is unavailable.

If you know when service will resume, an HTTP `Retry-After` header can communicate that timing. [MDN's 503 reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status/503) explains the response and header.

## Use 429 for rate limiting

A 429 says the client has sent too many requests in a given period. It is appropriate when you are throttling a requester, not when every visitor receives an outage. Again, `Retry-After` can tell a client how long to wait. See [MDN's 429 reference](https://developer.mozilla.org/en-US/docs/Web/HTTP/Status/429).

## What this means for crawling

Google's [crawler guidance](https://developers.google.com/crawling/docs/troubleshooting/http-status-codes) says 5xx and 429 responses can make its crawlers temporarily slow down. Persistent errors can have more serious consequences for indexing. Its [troubleshooting guide](https://developers.google.com/search/docs/crawling-indexing/troubleshoot-crawling-errors) discusses temporary use of 503 or 429 during overcrawling and warns against leaving those responses in place for days.

Do not use 401 or 403 as a generic crawl-rate control. Those codes mean access is restricted, and Google handles them differently from temporary server problems.

## Recovery checklist

After an incident, check that affected URLs return their intended final status, redirects still work, and important pages no longer carry an accidental `noindex`. Compare logs and monitoring across the outage window. A single successful spot check confirms current behavior from one network; it cannot prove the issue was absent at every point in time.
